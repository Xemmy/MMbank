# MMbank — Ideas Backlog

*Research-only document. Nothing here is implemented; nothing here is
committed to. Written against the tip of `claude/mmbank-local-ai-parsing-4cfi14`
(`79c931e`, `versionCode = 68` / `versionName = "0.42.0"`, schema **v24**).
Last updated: 2026-09-14.*

## How to read this file

`MMbank-PHASED-UPGRADE-PLAN.md` is finished and `MMbank-FEATURE-LOG.md` is the
per-phase record of what landed after it. This file is neither: it is a menu of
**candidate** work, gathered by reading the current source plus every `Deferred`
/ `Not covered by CI` note in the feature log. Pick from it; don't work through
it in order.

Each idea carries:

- **Why** — the concrete gap in today's code, with the file that shows it.
- **Sketch** — enough shape to judge the cost, not a design.
- **Schema** — whether it needs a Room migration (`CLAUDE.md`: bump
  `AppDatabase.version`, add an explicit `Migration` with raw SQL, never
  destructive).
- **Effort** — **S** (one sitting, no schema change), **M** (schema and/or
  several files), **L** (multi-phase).
- **Risk** — what could go wrong, especially anything CI can't catch.

### Standing constraints every idea inherits

1. **CI proves compilation only.** `lint-and-unit-tests` is
   `continue-on-error: true`, so the workflow stays green through failing
   tests; `-x lint` means lint never runs in that job. Read the "Run unit
   tests" step log, not the check mark. (`CLAUDE.md`, and the Phase 3 entry in
   the feature log where this trap actually bit.)
2. **JVM tests only.** There is no `app/src/androidTest` directory at all
   (0 files) and no Robolectric, so nothing touching Room, Compose, WorkManager
   or the Android framework is verifiable in CI. Ideas below that need device
   verification say so.
3. **Every new piece of logic gets a pure-JVM unit test in the same commit**,
   and any field added to `Entities.kt` must land in `Models.kt` and both
   mappers with a round-trip test in `EntityMappersTest` — plus
   `BackupManager.kt`'s `toBackup()`/`toEntity()` pair, which is a *fourth*
   place the same field has to appear and which has already silently dropped
   columns once (Phase 13.1).
4. **Bump `versionCode`/`versionName` in the same commit** for anything with
   APK-visible behavior.

## Theme A — Data integrity and the migration blind spot

The single largest structural risk in the project: 23 migrations have been
written and **none has ever been executed** anywhere in CI.

### 1. Commit the exported Room schema JSONs — **S**, high value

**Why.** `app/build.gradle.kts` sets `exportSchema = true` and a
`room.schemaLocation`, but `app/schemas/` does not exist in the repo. So there
is no record of what each schema version actually looked like, no
schema-vs-migration validation, and no basis for any migration test. The
handover flagged this at v9; the schema is now v24.

**Sketch.** Add `app/schemas/**/*.json` to git, generated by a debug build.
Since they can only be generated where the Android SDK runs, the generating
build has to be CI: add a workflow step that runs `:app:kspDebugKotlin`, then
uploads `app/schemas/` as an artifact to download and commit, or have the job
commit them back on `claude/**` pushes.

**Schema.** None (this records the schema, doesn't change it).

**Risk.** Low. Once committed, a forgotten `version` bump becomes a diff.

### 2. Room `MigrationTestHelper` suite — **M**, blocked on #1

**Why.** Idea #1's JSONs are the precondition for `MigrationTestHelper`, which
can then actually run `MIGRATION_1_2 … MIGRATION_23_24` against real SQLite.
Today every `ALTER TABLE` is verified by "it compiled and the SQL looks right".

**Sketch.** Needs `app/src/androidTest` and an emulator job in CI — the first
instrumented test in the project, so budget for the infrastructure, not just
the tests. Alternative at a fraction of the cost: **Robolectric** with real
SQLite in the JVM job, which would make migrations testable without an
emulator and would also unlock testing DAOs, `BackupManager` round-trips and
`WorkManager` workers.

**Risk.** Emulator jobs are slow and flaky; Robolectric is the pragmatic first
move. Either way this is the highest-leverage engineering investment available.

### 3. A single "migrate from v1" smoke test — **S**, cheap partial of #2

**Why.** Even without instrumentation, the full chain can be exercised in a
plain JVM test against an in-memory SQLite JDBC driver: create a v1 schema by
hand, apply each `Migration`'s SQL strings in order, assert the final table
shape matches the entities. It won't catch Room-specific validation, but it
would catch a typo'd `ALTER TABLE`, which is the realistic failure.

**Sketch.** Expose the migration SQL as data (a `List<String>` per step)
alongside the `Migration` objects so a JVM test can read it without an Android
`SupportSQLiteDatabase`.

**Risk.** Divergence between the exposed SQL list and what the `Migration`
actually executes — mitigate by having the `Migration` execute *from* the list.

### 4. Cross-check mapper completeness by reflection — **S**

**Why.** Phase 13.1 fixed backup/restore silently dropping transaction and
account columns. `BackupManager.kt:310` even carries a comment warning that
fields added to either class compile clean and write the wrong data. A comment
is not a test.

**Sketch.** A JVM test that reflects over `TransactionEntity`'s and
`AccountEntity`'s constructor parameters and asserts each name appears in
`BackupTransaction` / `BackupAccount` (with an explicit, documented
allow-list of deliberate omissions). Adding a column then fails the build until
you decide whether it belongs in a backup.

**Risk.** None meaningful. Do the same for `Models.kt` ↔ `Entities.kt`.

### 5. Backup format version negotiation test matrix — **S**

**Why.** The backup payload is at v4, and each bump has had bespoke "restoring
an older backup leaves this device's X alone" semantics (category data in one
step, the ignore list in another). Those rules live in prose.

**Sketch.** A table-driven test: for each historical payload version, a
canonical fixture JSON, and assertions on exactly which sections restore and
which are left alone. Fixtures also become regression bait for #4.

### 6. A `DatabaseEncryptionMigrator` failure-path test — **S**

**Why.** `DatabaseEncryptionMigrator.kt` / `SecureDatabaseFactory.kt` /
`SqliteFileFormat.kt` decide whether an existing DB is plaintext or SQLCipher
and migrate it. A wrong answer means an unopenable database and total data
loss, and it's the one code path where "restore from backup" may also be gone.

**Sketch.** `SqliteFileFormat`'s header sniffing is pure byte inspection and is
already JVM-testable — make sure truncated files, zero-length files and a file
whose first 16 bytes coincidentally look like the SQLite magic are all covered.

## Theme B — Multi-currency, the most-deferred gap in the log

Four separate `Deferred` notes say the same thing: everything analytical is
default-currency-only.

### 7. Convert at read time across every analytic surface — **L**

**Why.** Category budgets compare a cap against default-currency spend only;
the monthly report has "no multi-currency consolidation"; the copilot context
builder takes a `toBase: (Transaction) -> Double?` that returns null for
unconvertible rows and then `sumOf { ... ?: 0.0 }` — silently counting an
unconvertible transaction as **zero** rather than flagging it.

**Sketch.** One shared `AmountConverter` in `domain/` that takes the cached
`exchange_rates` table and returns a `Converted(value)` / `Unconvertible(code)`
result, and make every call site handle the second case explicitly instead of
`?: 0.0`. Then thread it through `CategoryBudgetCalculator`,
`MonthlyReportBuilder`, `FinancialHealthEngine`, `AnalyticsViewModel` and
`FinancialCopilotQueryHandler`.

**Schema.** None — `exchange_rates` already exists.

**Risk.** Wide blast radius. Worth doing as: (a) introduce the type and make
unconvertible rows *visible* (Home already has the "≈" convention), then
(b) migrate call sites one phase at a time.

### 8. Historical rates instead of today's rate — **M**

**Why.** `ForexApi` has exactly one endpoint, `v6/latest/{base}`. A purchase
made 8 months ago is converted at today's rate, so last year's report changes
every time rates move.

**Sketch.** Store a rate snapshot per (day, pair) as transactions are recorded,
and convert historical rows at their own date's rate, falling back to latest.
`open.er-api.com`'s free tier has no history endpoint, so the snapshot must be
built forward from now — which means it's worth starting early even if the
payoff is a year out.

**Schema.** New `exchange_rate_history` table, or a `dayKey` column on the
existing table plus a composite key.

### 9. Flag unconvertible totals rather than under-reporting — **S**

**Why.** A standalone, cheap slice of #7: anywhere a total is shown, if any
contributing row was unconvertible, say so. Today it just quietly reads low.

### 10. Per-account display currency on the Dashboard — **S**

**Why.** A UAE user with an AED salary and a USD card wants both figures, not
one blended number. The `Account` model already carries `currencyCode`.

## Theme C — Capture, parsing and the ingest path

### 11. Import the device's SMS inbox directly — **M**

**Why.** Phase 14 built a *paste* importer, which exists because the app holds
`RECEIVE_SMS` but not `READ_SMS` (see the manifest — only `RECEIVE_SMS`,
`INTERNET`, `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, `USE_BIOMETRIC`,
`POST_NOTIFICATIONS`). Pasting hundreds of messages by hand is the worst part
of onboarding, and all the machinery to process them already exists.

**Sketch.** Add `READ_SMS`, a sender-and-date-range picker, and feed
`Telephony.Sms.Inbox` rows through `ImportPastedMessagesUseCase`'s existing
path (which already sets `TransactionSource.PASTED`, resolves dates via
`MessageDateExtractor`, dedups on `findByRawMessage`, and — per Phase 14.1 —
correctly declines to spend AI budget on a bulk import).

**Risk.** `READ_SMS` is a Play-restricted permission, but the README already
says this app is sideload-only and deliberately outside Play policy, so the
constraint doesn't bind. The real risk is a user importing 5,000 messages —
needs batching, progress and cancellation.

### 12. Make the importer resumable and cancellable — **S**, pairs with #11

**Why.** `ImportPastedMessagesUseCase` returns a `Summary` after processing
everything. A 2,000-message import that the user backgrounds halfway is
currently an unknown state.

**Sketch.** Move it into a `WorkManager` worker (the project already uses
WorkManager for bills, subscriptions, retention and AI) emitting progress.

### 13. Show *why* a message wasn't recognised — **S**

**Why.** `Summary.unparsed` is a count. The user's next question is always
"which ones, and what was missing?" — and the answer (no digits / matched a
rule but no plausible amount / no rule matched) is already computed inside
`TransactionParser`, which has a diagnostics sink.

**Sketch.** Surface the unparsed messages in a list with the parser's reason,
each with a one-tap "create a rule from this" that prefills `RuleEditorScreen`.

### 14. Generate a draft rule from an unparsed message — **M**

**Why.** Closes the loop from #13. Writing a regex with named groups by hand is
the steepest cliff in the app.

**Sketch.** Highlight the amount and merchant in the message text, then
synthesize the pattern around the selections. `AiSelfHealingRuleGenerator`
already exists for the AI path; this is the manual, deterministic sibling — and
the same "pending rules are never auto-applied" invariant should hold.

### 15. Rule test corpus, not a single sample — **M**

**Why.** `ParsingRule.sampleText` holds *one* remembered test string, and
`RuleHistoryTester` exists but a rule edit can silently break messages it used
to handle.

**Sketch.** Store N samples per rule with expected outcomes; run all of them on
save and show a pass/fail strip. This is unit-testable end to end.

**Schema.** New `rule_samples` table.

### 16. Detect and warn on rule shadowing — **S**

**Why.** Priority collisions are handled at match time (higher priority wins;
tie → longest signature; still tied → first registered plus a warning to the
diagnostics sink) but the user never sees the warning at *edit* time.

**Sketch.** On save, run the new rule against every other rule's stored samples
and report "this also matches 3 messages currently handled by *Tabby Card*".

### 17. Per-sender capture statistics — **S**

**Why.** The most useful diagnostic is "which senders are producing messages
that never parse". The data is in the ledger plus the ignore/unparsed paths;
nothing aggregates it.

**Sketch.** A Diagnostics card: sender → captured / ignored / unparsed counts
over 30 days, each row tappable into the rules screen.

### 18. Undo an ignore — and preview what it will mute — **S**

**Why.** `MessageSimilarity` falls back to Jaccard overlap at 0.75 for messages
of ≥4 tokens. A too-generic sample silently swallows real transactions, and the
feature log explicitly calls a false ignore "worse than letting noise through".

**Sketch.** Before saving an ignore pattern, run its fingerprint against the
last 500 stored `rawMessage` values and show what *would* have been dropped,
including any that became real transactions.

### 19. Ignore-list hit counter — **S**

**Why.** Same concern, after the fact: an ignore pattern that has fired 400
times in a week is probably too broad. Show a count and a last-fired timestamp
per pattern.

**Schema.** Two columns on `ignored_message_patterns`.

### 20. Currency and locale coverage audit for `TextNormalizer` — **S**

**Why.** `TextNormalizer` handles Arabic-Indic digits, `٫` as a decimal
separator and bidi stripping; `CurrencyNormalizer` maps symbols to ISO codes.
Neither has a systematic inventory of what's covered.

**Sketch.** A table-driven test enumerating every symbol/locale the app claims,
including the ambiguous cases (`$` for USD vs AUD vs CAD; `ر.س` vs `ريال`;
Eastern Arabic-Indic `۰-۹` as distinct from Arabic-Indic `٠-٩`).

### 21. Thousands-separator and ambiguous-decimal hardening — **S**

**Why.** `1.234` is one thousand two hundred thirty-four in much of Europe and
one-and-a-bit elsewhere. A misparse here silently books a 1000× wrong amount —
the worst class of bug this app can have.

**Sketch.** Decide the rule explicitly (group-size heuristics + per-rule
locale hint), document it, and pin it with tests including the genuinely
ambiguous cases.

### 22. Refund and reversal pairing — **M**

**Why.** `IngestCapturedMessageUseCase` special-cases Tabby "Transaction
adjusted" messages with `excludeFromStats = true`, and `TransferMatcher`
already pairs the two legs of a card statement payment via
`linkedTransactionId`. A generic refund is neither.

**Sketch.** Generalize `TransferMatcher` into a pairing engine: a credit that
matches a prior debit on amount + merchant within a window links to it and both
drop out of analytics, with the link visible and breakable in the UI.

### 23. Partial-refund handling — **S**, follow-on from #22

**Why.** A refund for *part* of a purchase can't be modeled by the symmetric
`linkedTransactionId` pair. Decide whether to net the original down or keep
both and mark the residual.

### 24. Pending → posted reconciliation — **M**

**Why.** Many banks send an authorization message and then a settlement
message with a slightly different amount (tips, FX). The ±2-minute dedup window
(`ABS(timestamp - :timestamp) <= 120000`) will not catch a settlement that
arrives two days later, so both land in the ledger.

**Sketch.** A `pending` flag plus a wider, amount-tolerant matcher that
supersedes rather than duplicates.

**Schema.** One column on `transactions`.

### 25. Make the dedup window configurable and observable — **S**

**Why.** ±2 minutes is a hardcoded constant chosen for the push+SMS pair. It is
also capable of eating a genuine second identical purchase.

**Sketch.** Expose the window in Settings (as an `AppPreferences` boolean-style
plain value, per `CLAUDE.md`'s guidance on which toggle shape to use), and log
every dedup decision to Diagnostics so a wrongly-dropped transaction is
recoverable rather than invisible.

## Theme D — Local AI (Gate-2)

### 26. Batch AI parsing instead of one call per message — **M**

**Why.** `AiDailyBudget` counts *requests*. Sending five unparsed messages in
one prompt costs one request instead of five, which for an on-device or
loopback model is nearly free in latency too.

**Sketch.** `AiTransactionPrompt` builds one message today; add an N-message
form with a strict indexed JSON response shape and extend `AiResponseParser`.

**Risk.** A malformed batch response loses all N results — needs per-item
fallback to single calls.

### 27. Show what the AI actually returned, per transaction — **S**

**Why.** `extractedMerchant` and `aiConfidence` are already persisted on
`Transaction` exactly so the Review screen can show what the parser/AI saw. The
full raw response only lives in `AiCallLogStore`, unlinked to the row it
produced.

**Sketch.** Link the call-log entry to the transaction id so the review card
can expand into the actual model output.

### 28. Confidence-threshold routing — **S**

**Why.** `AiConfidenceScorer` produces a 0–100 score, and
`needsCategoryApproval` gates AI category suggestions behind human approval —
but the threshold that decides "confident enough to not ask" is fixed.

**Sketch.** A user-set threshold in AI settings, with a live preview of how
many of the last 100 transactions would have been auto-applied at each setting.

### 29. Cost/latency dashboard for the AI path — **S**

**Why.** `AiCallLogStore` has the raw material; the AI settings screen shows a
daily counter. Requests/day, median latency, success rate and budget
exhaustion events would make the local-vs-remote decision concrete.

### 30. Offline queue when the AI endpoint is unreachable — **S**

**Why.** `AiParsingWorker` runs on WorkManager, but a message that misses while
the loopback model is down is presumably just lost to `NoMatch`.

**Sketch.** Retain misses in a bounded queue and re-run them when the endpoint
returns, respecting the same daily budget.

### 31. Let the copilot answer without a model — **M**

**Why.** `FinancialCopilotQueryHandler` builds a context (category totals,
merchant totals) and then a *prompt* — so every question requires a working AI
endpoint. But the top ten questions ("how much did I spend on dining last
month", "what's my biggest merchant") are pure queries over data the handler
has already computed.

**Sketch.** A small intent matcher that answers the common shapes directly and
falls through to the model for everything else. Fully JVM-testable, and makes
the copilot useful on a device with no model configured.

### 32. Suggested-question chips in the copilot — **S**

**Why.** An empty chat box with no model configured is the app's weakest first
impression. Chips generated from the user's own top categories/merchants both
teach the feature and feed #31.

### 33. Redaction audit for anything leaving the device — **S**

**Why.** `LogRedactor`, `LoopbackGuard`, `AiForwardGate` and
`AiProviderMode.LOCAL` (loopback-only, enforced in code *and* by the network
security config) form a careful privacy story. It deserves a single test file
that asserts the whole chain: with `LOCAL` mode set, no non-loopback host is
reachable; with remote mode, the prompt contains no account numbers, IBANs or
full card digits.

## Theme E — Analytics, insights and reporting

### 34. A real line/sparkline chart primitive — **S**

**Why.** The Phase 4 `Deferred` note says the merchant monthly trend is
bars-per-month because `CanvasCharts.kt` contains only `PacingArcGauge` and
introducing a chart primitive wasn't worth it for one screen. There are now
several screens that would use one (merchant detail, goals, net worth, cash
flow), which changes the arithmetic.

**Sketch.** One `Canvas`-based sparkline with the Obsidian theme tokens, unit
tested at the path-geometry level (pure math, no Compose).

### 35. Net-worth history — **M**

**Why.** Net worth is computed live from account balances plus Binance, so
there is no "net worth over time" anywhere. `NetWorthAggregator` exists but has
nothing to remember.

**Sketch.** A daily snapshot row (WorkManager, same shape as the existing
retention worker), then a chart via #34.

**Schema.** New `net_worth_snapshots` table.

### 36. Year-in-review — **M**

**Why.** `MonthlyReportBuilder` + `MonthlyReportHtmlFormatter` already produce
a full report; an annual variant is mostly new aggregation over the same
machinery. Note the formatter's escaping trap (a `rawLabel` path skipped
escaping and shipped an XSS-shaped bug in Phase 3) — any new row type needs a
markup test.

### 37. Category drill-down from every chart — **S**

**Why.** The Dashboard's by-category breakdown and the Analytics donut are
terminal: you see that Dining is 2,400 and can't get to the transactions.

**Sketch.** Route into `TransactionsScreen` with the filter pre-applied — the
filter bar already supports category, date range, account and person.

### 38. Month-over-month deltas on every headline number — **S**

**Why.** "Spent 4,210 this month" means nothing without "up 18% on August".
`HeroSpendSummaryCard` just gained Received and Remaining alongside Spent
(commit `79c931e`), so the card is already the right home for one more.

### 39. Anomaly detection on merchant spend — **M**

**Why.** `MerchantProfiler` and `SubscriptionRadarEngine` already establish
per-merchant baselines. A charge well outside a merchant's own distribution is
the single most valuable alert a finance app can send.

**Sketch.** Per-merchant median + MAD, flag outliers, surface in Insights with
an explicit "this is 3× your usual Careem fare" rather than a bare number.

**Risk.** False positives destroy trust fast; require a minimum history and
tune conservatively.

### 40. Recurring-income detection beyond payday — **S**

**Why.** `CashFlowForecaster` detects a paycheck pattern and
`PaycheckSchedule` allows a manual day-of-month override. Rent received,
dividends and refunds are recurring income the forecaster ignores.

### 41. Weekday/time-of-day spending patterns — **S**

**Why.** `SpendingHeatmap` exists for the calendar view. The same data answers
"you spend 40% of your dining budget on Thursdays", which is actionable in a
way a heatmap isn't.

### 42. Cash-flow forecast confidence band — **S**

**Why.** `CashFlowForecaster` produces a projection; a single line implies more
certainty than the input supports. Show a band derived from historical variance.

### 43. "What changed" digest — **S**

**Why.** `AiWeeklyDigestGenerator` exists. A deterministic sibling — new
subscriptions detected, price changes, budgets crossed, unusual merchants — is
more reliable and needs no model.

## Theme F — Budgets, bills, goals

### 44. Envelope budgeting / rollover — **M**

**Why.** `CategoryBudgetCalculator` and `DailyBudgetPacing` treat each month as
independent. Under-spending on groceries in August should be able to carry into
September; that's the mechanic that makes category budgets stick.

**Schema.** A per-category, per-month rollover balance.

### 45. Per-bill reminder lead time and snooze — **S**

**Why.** Explicitly deferred in Phase 6: the 3-day window
(`SubscriptionReminders.DEFAULT_WINDOW_DAYS`) and a global on/off are the only
controls.

**Schema.** One nullable column on `bills`.

### 46. Un-mark a bill as paid — **S**

**Why.** Also from Phase 6: `markPaid` has no undo, and a recurring bill's due
date can't be pushed back. `BillAdvancer` advances by calendar `Period` (Phase
13 fixed nominal-day drift), so reversing is symmetric and testable.

### 47. Due-date picker for bills and goals — **S**

**Why.** Both `BillsScreen`'s add dialog and `GoalsScreen`'s `AddGoalDialog`
skip a date picker and use "due in N days" to avoid `DatePickerDialog`
complexity. Material 3 has `DatePicker` in Compose now; one shared wrapper
serves both.

### 48. Link a bill to the transaction that paid it — **M**

**Why.** Marking a bill paid is currently an assertion, disconnected from the
ledger. Matching it to a real transaction makes "paid" verifiable, and
mis-marks recoverable.

### 49. Multiple price changes in subscription history — **S**

**Why.** Phase 2's `Deferred`: `previousAmount` records only the *last* change,
so a subscription that rose twice reports one step.

**Sketch.** A price-history child table, or a serialized list; the radar engine
already segments the series to find the change.

### 50. Subscription cancellation assistant — **S**

**Why.** The radar tells you a subscription exists; the next step is always
"how do I stop it". A per-merchant notes/URL field plus a "cancelled on"
state closes the loop instead of leaving the row to be dismissed.

### 51. Goal auto-allocation rules — **S**

**Why.** Goals support "Auto-Allocate Surplus" at month end. A percentage-of-
income rule (or round-up-every-purchase) makes goals fill continuously rather
than in one lump.

### 52. Debt payoff planning — **M**

**Why.** `Account` already carries `outstandingBalance`,
`nextInstallmentAmount`, `dueDayOfMonth`, `profitRatePa`, `maturityDateMillis`
and an `earlySettlementFeeEstimate` heuristic. Everything needed for an
avalanche/snowball comparison across multiple debts is already modeled and
completely unused beyond a single-account estimate.

**Sketch.** Pure-domain payoff simulator (perfectly JVM-testable) plus a screen
comparing strategies and showing total profit paid under each.

## Theme G — Splits and shared expenses

### 53. Settle up through the ledger — **M**

**Why.** `SplitType.SETTLEMENT` records a settle-up inside the group's own
balance math, but a real settlement is also a real transaction. The two ledgers
don't meet.

**Sketch.** Optionally link a `GroupExpense` to a `Transaction`, so recording a
settlement can either create the transaction or match an existing one.

### 54. Split an existing transaction into a group — **S**

**Why.** The natural flow is "this dinner I just captured, split it with the
group" — today a group expense is entered from scratch, retyping an amount the
app already has.

**Sketch.** A "split this" action on `TransactionDetailSheet` that opens the
group picker and prefills `SplitAllocator`.

### 55. Export a group's balances — **S**

**Why.** `DebtSimplifier` computes the minimal set of payments. Sharing that as
text is one intent away and is the moment the feature actually gets used —
note the app currently has exactly one `ACTION_SEND` (sharing a diagnostics
log, `SettingsScreen.kt:2366`) and **no `FileProvider`** in the manifest, so
file sharing needs that added first.

## Theme H — UX, navigation, polish

### 56. Split the two 2,500-line screens — **M**

**Why.** `TransactionsScreen.kt` is 2,571 lines and `SettingsScreen.kt` is
2,417 — together 16% of the app's 31k lines. Both are also the only files
producing deprecation warnings in CI. Everything else in `ui/screens/` is under
930 lines, so these two are the outliers, not the norm.

**Sketch.** `SettingsScreen.kt` still contains the bodies of ~14 subpage
composables that already have their own routes in `MainActivity`; moving each
into its own file under `ui/screens/settings/` is mechanical and low-risk.
`TransactionsScreen` splits along list / editor-dialog / bulk-mode seams that
already exist as private composables.

**Risk.** Pure churn if done carelessly; do it as a no-behavior-change commit
so the diff is reviewable, and clear the deprecations in the same pass.

### 57. Search that spans more than the Activity tab — **S**

**Why.** Full-text search exists on transactions only. Accounts, rules,
subscriptions, bills, goals, groups and settings are all findable only by
navigating to them — and there are now 30+ routes.

**Sketch.** One command-palette-style search entry.

### 58. Undo for destructive actions — **M**

**Why.** Deleting a category or person now reassigns rather than orphaning
(Phases 12–12.2), which is the hard part — but there's still no undo, and the
retention prune deletes transactions outright with no preview (Phase 5's
`Deferred` explicitly notes there is no "what would this delete" view and no
forced backup gate).

**Sketch.** A snackbar-level undo for row deletes, plus a dry-run preview for
the prune worker showing counts by year before the first run.

### 59. Onboarding that matches the README's setup dance — **M**

**Why.** First-run requires: SMS permission, then notification access via the
Android 13+ "Allow restricted settings" flow (a **⋮ menu inside system
Settings** most users will never find), then battery-optimization exemption,
then currency, then optionally Binance keys. That's five steps documented only
in the README of a repo the user of the app may never read.

**Sketch.** A guided first-run flow with live permission state per step and an
illustration of the restricted-settings menu, which is the step that actually
blocks people.

### 60. Capture-health banner — **S**

**Why.** The failure mode of this app is silent: notification access gets
revoked by an OEM battery manager and capture just stops. Nothing notices.

**Sketch.** Track last-captured-message time; if the listener is disconnected
or nothing has arrived in N days while the permission is nominally granted,
show a persistent banner. This is arguably the highest-value small idea in the
file, because it protects every other feature.

### 61. Quick-settings tile / notification action for manual entry — **S**

**Why.** Adding a cash transaction requires opening the app and navigating to
Activity. A tile or an ongoing-notification action makes cash tracking
plausible rather than aspirational.

### 62. More home-screen widgets — **S**

**Why.** `DailyBudgetWidget` is the only Glance widget. Net worth, upcoming
bills and a top-categories widget reuse existing domain code almost entirely.

### 63. Widget configuration — **S**

**Why.** `DailyBudgetWidgetReceiver` has no configuration activity, so the
widget shows one fixed thing. Even a size-aware layout would help.

## Theme I — Security and privacy

### 64. PIN fallback for app lock — **S**

**Why.** `AppLockController` + `BiometricAuthManager` gate the app on
biometrics. A device with a failed fingerprint sensor, or a user whose
enrollment changes, is locked out of their own ledger with no second factor.

### 65. Screenshot blocking while locked or on sensitive screens — **S**

**Why.** `hideBalances` exists as a reactive `StateFlow` on `AppContainer`
precisely because balance privacy matters here. `FLAG_SECURE` on the lock
screen (and optionally app-wide) is a two-line, high-value complement, and also
removes the app's contents from the recents thumbnail.

### 66. Backup password strength and recovery guidance — **S**

**Why.** `BackupCrypto` encrypts with AES-256 from a user password. A forgotten
password means the `.mmb` is unrecoverable, and nothing in the flow says so
loudly enough or checks the password is non-trivial.

### 67. Scheduled automatic backups — **M**

**Why.** Backup is entirely manual. The WorkManager pattern is established four
times over (bills, subscriptions, retention, AI), so a weekly encrypted export
to a user-chosen SAF directory is a well-trodden path.

**Risk.** Where it writes matters; requires a persisted SAF tree URI.

### 68. Audit trail for balance corrections — **S**

**Why.** Balance corrections post an auditable "Balance adjustment" transaction
with `excludeFromStats = true` (the rule name is a shared constant, kept in
sync across files by a cross-file test). What's missing is the *before* value,
so you can't reconstruct why a correction was 340 rather than 34.

## Theme J — Engineering hygiene

### 69. Make CI actually fail on failing tests — **S**, highest hygiene value

**Why.** `continue-on-error: true` on the "Run unit tests" step is the single
most expensive line in the repo. The feature log documents it masking a real
assertion failure (Phase 3) and a real compile error (Phase 6), and every
verification note in that file exists as a manual workaround for it.

**Sketch.** Remove `continue-on-error` from the unit-test step and let
`final-status` gate on it too. If the intent was "don't block the APK build on
tests", keep that by making `build-apk` not depend on the test job's success
while still failing the workflow overall.

**Risk.** If the suite has any latent flakes, this surfaces them immediately —
which is the point, but sequence it deliberately.

### 70. Re-enable lint as its own non-blocking job — **S**

**Why.** `-x lint` means lint never runs despite the job being named "Lint &
Unit Tests". Separately, `NullSafeMutableLiveData` is disabled in
`app/build.gradle.kts` purely to work around a lint *crash*
(`IncompatibleClassChangeError` between lint's bundled Kotlin analysis API and
Kotlin 2.0.21) — that suppression should be dropped once AGP ships a matching
lint, and nothing currently tracks that.

### 71. Toolchain upgrade pass — **M**

**Why.** AGP 8.7.3 / Kotlin 2.0.21 / Room 2.6.1 / `compileSdk` 35, against a
Compose BOM already at `2025.12.00` — the Compose side is far ahead of the
build tools. Upgrading AGP and Kotlin is also the actual fix for #70's lint
crash, and Room 2.7+ brings its own improvements.

**Risk.** KSP version is pinned to Kotlin (`2.0.21-1.0.27`), so these move
together. Do it in isolation from feature work — a green APK build is a real
signal here, which makes this one of the few changes CI genuinely verifies.

### 72. `targetSdk` 36 readiness — **M**

**Why.** `targetSdk = 35`. Each bump tightens background execution and
notification rules — exactly the two things this app depends on.

### 73. Screenshot/snapshot tests for the theme layer — **M**

**Why.** `ObsidianTokens`, `Glass`, `Glow`, `AmbientBackground`, `DesignMode`
and `BackgroundStyle` form a substantial theming system with no visual
regression coverage. Paparazzi runs in the JVM, so this fits the existing
CI shape without an emulator.

### 74. Baseline profile — **S**

**Why.** A Compose app of this size on a cold start benefits measurably, and
generating one is a well-worn recipe.

### 75. Strict-mode and leak checks in debug builds — **S**

**Why.** Two long-lived services plus four WorkManager workers plus SQLCipher
is exactly the shape where a leaked context goes unnoticed.

## Theme K — Accessibility and localization

### 76. Extract strings — **M**

**Why.** `app/src/main/res/values/strings.xml` is **6 lines**. Every user-facing
string in ~31k lines of Compose is hardcoded English.

**Risk.** A very large, very boring diff that touches nearly every UI file. Do
it per-screen, and do it *after* #56 splits the two big screens or it will be
unreviewable.

### 77. Arabic UI and RTL — **M**, depends on #76

**Why.** The app already parses Arabic bank SMS (Arabic-Indic digits, `٫`
decimal separator, bidi stripping) and the manifest already sets
`android:supportsRtl="true"` — so it takes Arabic input seriously while
presenting an English-only interface. The mismatch is conspicuous.

### 78. Content descriptions and touch targets — **S**

**Why.** The UI leans on emoji and icon-only chips (`SpendingCategory` carries
an emoji per entry; accounts, goals and groups all have icon fields). Emoji are
announced unpredictably by TalkBack, and icon-only chips frequently fall below
the 48dp minimum.

### 79. Number formatting by locale — **S**

**Why.** `FinancialCopilotQueryHandler.money()` is
`String.format(Locale.US, "%.2f", amount)`. `Locale.US` is right for a *prompt*
(stable machine-readable input) and wrong anywhere a human reads it — worth
auditing `ui/util/Format.kt` and `AmountText.kt` for the same pattern and
making the distinction explicit rather than incidental.

### 80. Dynamic type and large-font layouts — **S**

**Why.** Dense financial rows (`RowComponents.kt`, the transaction cards, the
hero card's now-three figures) are the first thing to break at 200% font scale.

## Suggested first slice

If the question is "what would I actually do next", in order:

1. **#69** (make CI fail on failing tests) — everything else is easier to trust
   afterwards, and it retires the manual verification ritual that every entry
   in the feature log currently performs by hand.
2. **#60** (capture-health banner) — small, and it protects the feature the
   whole app is built on from failing silently.
3. **#1 → #2/#3** (commit schema JSONs, then Robolectric migration tests) —
   closes the only gap with data-loss consequences.
4. **#11** (import the SMS inbox) — the largest single user-visible win, and
   it reuses a pipeline that already exists and is already tested.
5. **#7** (multi-currency at read time) — the most-repeated `Deferred` note in
   the log; start with #9 so wrong numbers at least become *visible* numbers.

## Explicitly not recommended

- **Play Store distribution.** `NotificationListenerService` + `RECEIVE_SMS` is
  a deliberate, documented choice; #11 would add `READ_SMS` on top. Sideload
  is the design, not a limitation to fix.
- **A cloud sync backend.** Every privacy property this app has —
  loopback-only AI, SQLCipher at rest, encrypted local backups, keys in the
  Android Keystore — derives from nothing leaving the device.
- **Switching off manual DI.** `AppContainer.kt` is 790 lines and works; Hilt
  would be churn with no user-visible payoff.
